Paquete privado compilado con PRODUCT exacto más un módulo propio cfg(test,windows), sin funciones originales modificadas. Otros helpers del padre previamente aceptados no se reaceptan por conteo.

Revisión: close_checked consumes self, invoca CloseHandle sobre su propio handle y captura last_os_error inmediatamente en fallo. close_with éxito hace forget(self), suprimiendo el segundo cierre de OwnedHandle; fallo devuelve CloseFailure con error y el mismo ChildJob, reteniendo autoridad para reintento. No extrae un raw handle con propietario eliminado antes de conocer resultado. Debug no mueve ni expone autoridad. Callback privado tiene precondición explícita: Ok sólo si cerró exactamente el handle; Err si sigue poseído. Uso de callback para inyección no acredita fallo natural Win32. Rama noWindows devuelve Unsupported con job retenido; sólo revisión estática, sin afirmar ejecución nativa Unix.

Oráculo propio escrito antes de runtime: dos fallos inyectados previos a CloseHandle conservan mismo valor HANDLE y GetHandleInformation válido; reintento éxito ejecuta closure una vez y cierra exactamente aquel HANDLE; sentinel CreateEvent creado después del cierre debe seguir válido después de retorno incluso si Windows reutiliza el slot; llamada real close_checked sobre otro Job propio consume/invalida su handle.

Control nativo propio PASS. Windows efectivamente reutilizó slot (OWN_CLOSE sentinel_slot_reused=true), por lo que además del razonamiento estático, el sentinel demuestra que el destructor no cierra por segunda vez aquel número tras cerrar el Job. Ambos errores fueron cierres omitidos deliberadamente por closure, no errores de kernel. No proceso hijo necesario dentro de esos Jobs vacíos: prueba de close primitive no de kill/reap.
