## 5.1. D4B-R01: dato semántico cacheado frente activación nueva

El plazo de una operación gobierna recepción/publicación de su resultado y su activación; no destruye retroactivamente un dato inmutable recibido y validado dentro de aquel plazo. Se separan tres tipos privados; ninguno añade wire ni constructor público de Vec:

- `OriginalColorProof`: key/input owner exactos y binding original generation/request/viewport/context, comprobación final D4a+status actual antes de aceptar el evento, y instante de aceptación `accepted_at < original_deadline`. Lo construye exclusivamente el scheduler al recibir el `RetainedSyntaxEvent::Styles` validado y comprobando que todavía corresponde a su demanda original; no se obtiene de hash, de un booleano suministrado por caller o de un evento ya tardío. El proof se conserva inmutable: no cambia id/request/plazo para hacer pasar otro evento. Un error/cancel/stale anterior a aceptación impide crear dato de cache.
- `CachedCodeData`: `CodeBlockKey`, snapshot/map/input dueños, Arc<RetainedRoleSet> admitido, `OriginalColorProof` y `SemanticCoverage`. Datos/owners/cargos originales sobreviven a aliases; el input puede conservar su OperationContext original ya vencido sin convertirlo en contexto actual ni invocar de nuevo from_receipt. Únicamente datos previamente acreditados entran en cache; no se deserializan aquí otros roles ni se renueva worker progress/deadline. Crear slot/key/proof y contenedor cache cobra capacidades reales al mismo ConsumerBudget; no clona vector/map/String. Preservar datos no autoriza dibujar color por sí mismo.
- `CodeActivation`: candidato de activación con Arc<CachedCodeData>, binding consumidor NUEVO, `FrameAuthority` y ColorOperationContext ACTUALES, más query/viewport acreditados. Se crea sólo mediante la demanda real del owner común D2/D4; no existe factory `newOperation(bool)` ni se considera una llamada repeated poll/redraw como acción2. Una acción2 auténtica recibe el nuevo operationId/Instant a su entrada conforme política §6, exactamente como una petición real; eso no renueva operación1. El mismo descriptor conserva su contexto entre poll/resize/supersede. Metadata nueva de activación/aliases se preadmite y cobra con tamaño/capacidad real; fallo→Plain local conservando T.

`SemanticCoverage` se acredita con la request que D4a validó completa: `All` corresponde a todo CodeText; `View` almacena rango cerrado de líneas CodeText, fuente/input idénticos y extremos raw byte/UTF8 derivados de lineStarts del snapshot. Conserva cobertura de líneas vacías explícita, sin inferir cobertura sólo de presencia de RoleSpans. No afirma que spans de una ventana cubran líneas no solicitadas. Query run/local→rawpayload sigue §3 y debe estar dentro de la cobertura acreditada; no Source Origin/projected ni salto de un Run vacío al siguiente.

Secuencia de hit: (1) D2 completa T y admisión/render mandatory y el owner recibe demanda genuina actual; (2) lookup cobrado compara Document propietario/Sourceidentity/Profile/Block/Domain/lenguaje/payloadkey y conserva leases; (3) comprueba contexto/cancel/binding actual sin volver a usar el plazo original como plazo de activación; (4) comprueba cobertura COMPLETA de viewport solicitado; (5) construye candidato CodeActivation cobrado; (6) D4c futura consume permiso de lookup/overlay SAME Work y vuelve a comprobar ColorContext y FrameAuthority antes commit. El dato antiguo no se presenta como mensaje o receipt de worker nuevo ni aparece un Ready de generación nueva fabricado. Plain render conserva autoridad separada y no depende del plazo de color.

`CodeRoleCursor` requiere una activación vigente ligada a ese key y viewport, no acepta directamente CachedCodeData o bindingoriginal como autoridad. Consulta sólo índices/map/spans previamente validados; no rehash/reUTF8/flatten todo el bloque en un cache hit, ni nueva visit_coverage textual. Reserva/búsqueda/comparaciones/roles usan el mismo permiso Work futuro, sin otra allowance. Si color vence entre crear candidato y commit, descarta activación/overlay y publica Plain T; el dato cacheado sigue retenido sólo si política/quota permiten. Cancel/stale global o source/profile/key cambiado no se cura creando nuevo contexto sobre el mismo frame.

Cobertura igual o subconjunto permite reutilizar datos; viewport fuera o parcialmente fuera de cobertura NO entrega color parcial desde esa entrada: Plain íntegro mientras se admite/pide nueva request real con el contexto actual original y un solo scheduler/child. Sólo puede usar la conexión del bloque actual bajo la igualdad contextual y de owner exacta de §5.2. Si el contexto de la demanda es distinto, incluso con key igual, debe retirar y acreditar reap antes de input contextual nuevo/set/Init. Un hit cache completamente cubierto no necesita worker ni esta transición. No se convierte View en All por spans contiguos ni se fusionan dos entradas para fingir cobertura de un hueco. Nueva request no revive operación1. Otra Source/Document/Profile/key descarta asociación; puede conservar cache válida de A por lease y quota para retorno auténtico posterior, sin usarla en B.

No trabajo opcional retiene autoridad textual: fallos/expiración sólo color→Plain; identity/cancel y deadline obligatorio T si normativo se comprueban aparte. La política cache es opcional/bounded; si memoria/capacidad de slot/activación no cabe, no cache o Plain sin tocar fuente ni exigir nueva segmentación T. Expulsión de un slot no borra allocation mientras roles/frame/IO tengan Arc; último alias libera exactamente sus cargos. El cached input con plazo viejo es lease/dato, no licencia para escribir nuevo Init, Supersede o Continue con contexto viejo.

## 5.2. D4B-R02: identidad contextual de conexión y miss de cobertura

`ConnectionIdentity` privada es `{CodeBlockKey, retainedInputOwner exacto, OperationContext activo}`. La igualdad de contexto usa la comparación D4a completa: id, Instant original y Arc cancel idéntico; un mismo id con otro plazo/cancel no coincide. Conserva también generation vigente y revisión del document/set actual. `WorkerDemandBinding` enlaza esa identidad con la request/viewport vigente; un supersede permitido crea request nueva checked en la misma conexión/contexto, sin cambiar generation/input/plazo. No exige igualdad del número de request antiguo para supersede, pero sí relación acreditada por el scheduler y su estado actual.

La selección del camino sucede después de admitir T y evaluar cobertura de la cache: hit completamente cubierto activa dato semántico bajo nueva autoridad sin IO/Init, aunque contexto viejo de su input haya vencido. Eso no vuelve vigente la conexión vieja. Miss total/parcial necesita worker y aplica estas reglas, en este orden:

1. Si key/input/context activo son exactamente los de la demanda y aún vigentes, puede request/supersede mediante la API D4a correspondiente. Comprueba binding y fase original antes del IO y recepción/publicación. Nunca envía Continue/Request con input de operación1 y contexto de operación2.
2. Si contexto activo difiere, está vencido/cancelado/stale, o key/input cambia, retirar el owner anterior: pause_document, esperar receipts físicos de IO joins/child wait/Active0/checked pipe+Job close y estado Reaped; Pending preserva owners/cargos y bloquea siguiente spawn. Incluso key semántica igual requiere esta transición. El reap no es éxito de la petición fallida y sticky original permanece separado. No cambio mutable del contexto de un input/Connection existente.
3. Tras Reaped, comprobar otra vez la demanda de acción2 (identity/cancel/deadline original). Preparar por el mismo DocumentPreparationOwner un NUEVO RetainedSyntaxInput contextual ligado a operación2 y sus cargos; map/key semánticos inmutables pueden compartirse por Arc si su owner/cuota/identidad exactos lo permiten, pero no se rebindea el inputString de operación1 ni se fabrican recibos del decoder. Copia nueva admitida al mismo ConsumerBudget, lineStarts/control metadata/capacity reales y coexistencia con cache/aliases viejos. Si no cabe snapshot/input/mapmetadata/roles/body requeridos, Plain íntegro local o sin cache opcional no referenciada, sin tocar fuente/T ni construir síncrono en UI.
4. FinalReceipt de preparación y join preceden set_retained_document/Init; decoder/roles nuevos quedan ligados al input2 y generation nueva checked. El contador monotónico avanza aunque BlockKey igual. CacheData1/proof1 siguen inmutables por sus leases, opcionalmente retenidos por quota; no se usan como autoridad de transporte2. Resultado2 valido puede reemplazar/añadir entrada dentro de límites, sin unir cobertura de huecos artificialmente.

Toda esta cadena conserva el mismo ColorOperationContext2 creado por la acción2 al ingreso: reap/preparación/cola/set/Init/chunks/request/progress/supersede/publicación no crean Instant nuevo. Cada fase usa min(original2,phase). Si operación2 vence durante retiro, espera física/prepare o Init, Plain2 y cleanup conforme contrato; no prolonga el plazo por arrancar el worker después. El reap puede seguir siendo obligatorio para seguridad física sin permitir trabajo nuevo opcional vencido. FrameAuthority/Plain textual independiente y cancel/stale normativos permanecen.

Ejemplo normativo: View0..4 de op1 aceptada, d1 vence, acción2 solicita View4..8. Coverage parcial implica miss completo (sin color parcial). El scheduler no puede pedir View4..8 a Connection1 ni asignar Context2 al input1. Ejecuta retiro/reap, input2 cargado y preparado en background, set/Init generation nueva bajo d2original, View4..8. Si cache1/aliases consumen presupuesto y no cabe input2, resultado Plain íntegro sin newInit; eviction sólo libera cargos reales al último alias. No nueva API wire, interfaz renderer, nuevo presupuesto ni segundo owner. Las APIs realesen D4a fijan contexto en set/input/Connection; esta transición las respeta en vez de asumir rebind in situ. Ese handshake es dependencia explícita D2b2/D2c, no propiedad ya probada por esta biblioteca. El fallback Plain por cuota snapshot/roles/cache siempre local.

Para recepción nueva/activación de una misma operación, OperationContext D4a es host id/deadline/cancel; D4b guarda además modo cerrado Inline|Tui en binding. Inline constructor t0+min(inline_total,5s) ANTES cualquier snapshot/cola/kernelstart y comparte exactamente id/Instant entre fences. Tui acción legítima fija original al ingresar scheduler con techo viewport_total; supersede/resize preservan original. Fases min(original,phase-limit), no convertir remanente a duración y renovarla. timeout optionalcolor→Plain completo; ready de operación1 consumido después de su plazo no Styles ni activación de esa operación. Reutilizar dato semántico ya acreditado en una operación2 auténtica sigue §5.1: no se entrega Styles de operación1 como receipt de operación2. Source legacy conserva policy previa y duración propia. Mandatory frame identity/cancel/deadline normativo si existe permanecen distintos de plazo color; nunca invalidar permiso Plain por5s vencidos.
