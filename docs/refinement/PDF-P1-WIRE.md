# PDF P1: framing, geometría y alfa R5 candidata

2026-10-10. Candidata privada para adversario, NOT_RUN. Base f8017f1; R4 preservada como antecedente. Entrada normativa PDF-PRODUCT-INTEGRATION y sus26oráculos; no cambia RV204 ni aceptación de producto. Lectura focal root-pdf-p1-preparation identifica cuatro fuentes físicas. No código ni implementación adicional paralela. P1 porta supervisor Rust y valida integración exacta con perfil experimental; P2–P5 siguen obligatorios.

## Frontera de P1

BinarySnapshot original inmutable, supervisor Rust contenido y validador host independiente; operaciones Metadata, PageRaster y PageText. PageLinks y BookmarkBranch tienen IDs definidos pero UnsupportedOperation antes spawn en P1: se implementan en P4, no se aceptan respuestas vacías fingiendo capacidad. La CLI pública no cambia en este corte. Python únicamente peer/harness independiente. Nada de UI, gráficos terminal o búsqueda exhaustiva aprobado por este diseño.

Un request por proceso. Fuente<=1048576 bytes, páginas<=256, textoN/U/S<=65536 yB<=3U, raster<=4194304 bytes, heap controlado H<=40MiB yD<=24MiB, wire interno texto<=8070600 bytes, request10s, cleanup2s. Todos vienen del perfil experimental congelado. Wire externo tiene límite separado8388608 bytes por dirección; no es allowance extra de memoria. source input framing añade cabeceras dentro de ese techo. Expansion128MiB/100000 y resto producto permanecen P2.

## Wire R3PV versión1

Little-endian, sin padding implícito. Cabecera exactamente16 bytes: magicASCII R3PV en0..4; versionu16=1 en4..6; kindu16 en6..8; bodyLengthu32 en8..12; reservedu32=0 en12..16. Longitud TOTAL frame<=65552, por tanto body<=65536. Toda lectura valida cabecera/kind/cap/estado y suma checked antes reserve/bodyread. No JSON ni Debug ni longitud de string como framing.

Un stream pertenece a una única identidad. Init input y Begin output tienen body104 bytes: generationu64 en0, requestu64 en8 (ambos nozero); sourceLengthu64 en16; sourceSHA256[32] en24; physicalPageu32 en56; engineu32=1 en60; profileu32=1 en64; opu16 en68; reservedu16=0 en70; DLLSHA256[32] en72. Begin debe ser byteidéntico a Init validado por H, no adoptar metadata del worker como identidad. Cada frame posterior hereda esa identidad del stream único; frame de otro request no puede aceptarse sin cambiar framing/Begin y eso se rechaza. Op1 Metadata admite physicalPage0 para count sin cargar página o1..256 para geometría de una única página; Op2 Raster yOp3 Text tienen página1..256; Op4 Links yOp5 BookmarkBranch se rechazan antes spawn en P1. Engine1 corresponde al DLL7881x64 hash aprobado; no lookup global por nombre ni DLL indicada por contenido.

Kinds input:1Init;2SourceChunk;3SourceEnd;4RasterParams. RasterParams únicamente Op2, despuésInit antesSourceChunk. Kinds output:10Begin;11Metadata;12RasterDescriptor;13RasterChunk;14TextDescriptor;15TextChunk;16ContentFailure;17End. Unknown kind/version/flags/reserved/op/Profile y estado rechazan. Bodycaps fijos: Init/Begin104; SourceEnd40; RasterParams64; Metadata112; RasterDescriptor64; TextDescriptor16; ContentFailure16; End48; chunks65536. Todas longitudes fijas deben ser exactas, no<=.

SourceChunk body: absoluteOffsetu64 seguido1..65528 bytes. Offset empieza0 y cada chunk siguiente igual bytes acumulados; total exacto sourceLength. Fuentevacía emite cero chunks. SourceEnd body sourceLengthu64+SHA[32]; tras esto D exige EOF físico y vuelve a contrastar digest original antes cualquier PDFium API. H exige éxito writer flush y cierre físico observado; petición close/SourceEnd no habilita respuestas. RasterParams no forma parte del digest de fuente.

RasterParams64 y RasterDescriptor64: widthu32 en0; heightu32 en4; strideu32 en8; formatu16=1 BGRA8 en12; alphaModeu16=2 straight (componentes independientes del alfa) en14; physicalPageu32 en16; clockwiseRotationu16 {0,90,180,270} en20; reservedu16=0 en22; cropX0/Y0/X1/Y1 f64LE en24/32/40/48; scale f64LE en56. Todos finitos, cropX1>X0/cropY1>Y0 yscale>0. Width/heightnozero, stride=4*width checked ytotal=stride*height<=4194304. H calcula params propios antes envío según metadata física acreditada; si metadata previa falta, primero Op1 y después requestRaster separado. Descriptor debe repetir params exactos; worker sólo devuelve pixels bajo ese contrato. Coordenadas son points PDF y rastertop-left despuésrotación; no SourceExact derivada de bitmap. Host obtiene EffectiveNativeBBox y rotación mediante Metadata de la MISMA página/snapshot; elige crop dentro de ese bbox validado. Dimensiones checked ceil(cropWidth*scale)/ceil(cropHeight*scale), intercambiadas para rotación FINAL90/270. FinalRotation=(intrínseca+adicionalusuario)%360. La API de render ya compone geometría/rotación intrínseca: no pasar FinalRotation como rotación adicional ni ignorar el bbox efectivo. Para crop arbitrario P1 propone RenderPageBitmapWithMatrix con transform externo M tal que M(N(p))=D(p), donde N es transformación nativa por defecto y D la deseada especificada en deltaR3. Matriz/clipping requieren FFI nuevo whitelist, validación finite/invertible y AE independiente; datos/exports declarados no acreditan ejecución. Descriptor repite params exactos y nunca acredita SourceExact.

RasterChunk/TextChunk body offsetu64+bytes1..65528, contiguos sin duplicado/hueco. Metadata112: pageCountu32 en0, physicalPageu32 en4, intrinsicRotationu16 {0,90,180,270} en8, directMediaStateu8 en10, directCropStateu8 en11, reservedu32=0 en12. EffectiveNativeBBox x0/y0/x1/y1 f64LE en16/24/32/40; DirectMediaBox opcional en48/56/64/72; DirectCropBox opcional en80/88/96/104. Estados directos cerrados0Absent,1ValidDirect,2InvalidDirect; absent/invalid usan payloadceros y diagnóstico, no inventan cajas. Sólo State1 contiene coordenadas finitas del getter directo con x1>x0 e y1>y0; x0/y0 negativos son válidos. Página0 count-only no carga página y todos campos/resto bytes excepto count son cero. Página>=1 debe coincidir con Init y count real, EffectiveNativeBBox debe tener coordenadas finitas y dimensiones positivas (x1>x0, y1>y0), obtenido de FPDF_GetPageBoundingBox; no sustituirlo con getters directos. En7881 los getters Media/Crop consultan diccionario directo, mientras bbox efectivo resuelve herencia/fallback e intersección. DirectCrop ausente NO rechaza página válida. PageRange se diagnostica sin metadata inventada. NativeBBox es geometría derivada del motor, no prueba SourceExact ni prueba de que existieran esos cuatro valores en fuente. Toda metadata conserva la identidad del snapshot y se invalida al cambiar generación. TextDescriptor16: innerSchemau32=3 (R3UTv3); innerLengthu32<=8070600; qualityu32=1 NativeDerivedUnverified; reservedu32=0. TextChunk transporta streamR3UTv3 completo, fragmentado arbitrariamente incluyendo cabeceras, con validadorR3UT host incremental existente adaptado a Read segmentos. Nunca reservar innerLength de nuevo además de tablas/texto ni crear captura completa. Validar dentroR3UT identidad/page/counts/schema/original strides64/16/40 y UTF16/semántica completa; Unverified no prueba sourceExact. Memoria de fragmentación/scratch se cobra al mismo ledger.

Response grammar: Begin -> uno de Metadata / RasterDescriptor+RasterChunks / TextDescriptor+TextChunks / ContentFailure -> End -> EOF. La rama corresponde exactamente a op. ContentFailure16: codeu16 enumerado(1Corrupt,2Encrypted,3PageRange,4NativeAPI,5TextLimit,6RasterLimit,7PageLimit); stageu16 enumcerrado según deltaR5; nativeIndexu32; nativeCodeu32; reservedu32=0. Describe error contenido sólo tras input completo válido; faltaDLL/attach/setup/transfer/earlyfirstbyte se clasifica HostError en H y no se disfraza de ContentFailure.

End48: totalBytesBeforeEndu64 en0; frameCountBeforeEndu64 en8; SHA256[32] en16 de TODOS bytes anteriores de respuesta, cabeceras incluidas desdeBegin hasta último payload. No incluye End ni trailing. Host compara counts/digest, EOF observado sin error, exit0 y cleanup completo; End no es receipt física. Failure válida no publica artifact pero conserva diagnóstico tipado. Raster/text son requests separados y pueden tener estados distintos, nunca un TextFailure elimina un RasterReady ya validado.

## Autoridad de proceso, EOF y publicación

No reutilizar global SLOT de un adaptador ni crear allowance independiente. SessionActorAuthority presta una residencia PdfCallOwned única desde preflight hasta proof físico; mismo gate que otras familias. Constructor sin préstamo cerrado no es API. Queued->BootstrapHeld->Contained->Sending->Running->Validating->Cleaning->Ready/Failed/PendingCleanup. Arc snapshot/ledger/context/candidate/cancel se conservan en dueño común; aliases no liberan físicos. Cancel/stale/errorsticky impide publicación aun tras cleanup posterior.

Worker hidden entry bootstrap bloqueado antes LoadLibrary/PDFium/init/source. Parent crea startpipe, captura Child/Job/pipes antes siguiente operación falible, attach_verified/readback y sólo después START. Proponer ChildJob perfil PdfOneProcess con KILL_ON_JOB_CLOSE|PROCESS_MEMORY|ACTIVE_PROCESS_LIMIT ylimit1/512MiB verificados; conservar API y readback legacy sin cambiarlo globalmente. Job no heredable, herencia sólo startRead ystdin/out/err del hijo; handlewhitelist requiere implementación+control independiente, no asumir Command::spawn la prueba. No descendants/Launch/scripts. H externo al Job, nativeallocations ExternalNativeUnknown,512MiB committed distinto de ledger requested.

Parent reader observa primerbyte bajo la MISMA sincronización que transición WriterPhysicalCloseStarted/Closed. Close-inflight equivale conservador EarlyResponse; Closed sólo tras cierre real exitoso, nunca tras encolar SourceEnd. Writer posee File converted fromChildStdin y cierre checked reteniendo mismo handle ante fallo. Observer registra irreversible HostError si primerbyte antesClosed; no empezar validador ni publicar. Evaluar flush/close/readerEOF/threadpanic DESPUÉS joins; primeros erroressticky no se borran por exit0 posterior. No mutex duranteIO ni cleanup. UI sólopoll, sin wait/join vivo.

Pending retiene Child/Job/startpipes/stdio/threadhandles/mailboxes/source/candidate/ledger; gate continúa ocupado hasta childwait+active0+pipeclose+joins+Jobclose acreditados, o rama NeverSpawned demuestra cada recurso efectivamente retirado. Cleanup intenta todos aunque uno falle,2s por intento; retry MISMO owner nunca relabela error ni renueva10s original. Cerrando wrapper/drop de receipt no prueba cleanup. Unixunsupported diagnóstico hasta containment nativo probado. No OpenProcess rescate porPID/nombre.

- r90: (s*(y-y0),s*(x-x0))
- r180: (s*(x1-x),s*(y-y0))

## Delta R4: orden ABI y coordenadas con signo

El header físico binary-7881/include/fpdfview.h define FS_RECTF en orden left, top, right, bottom (cuatro float); no equivale al orden wire x0,y0,x1,y1. Después de retorno true del getter, mapear explícitamente x0=left, y0=bottom, x1=right, y1=top y promover cada float a f64. Nunca copiar los 16 bytes del struct al body ni reinterpretarlos como cuatro f64. False no autoriza leer outputs; inicialización cero no convierte fracaso en geometría válida. Los getters directos tienen su contrato de parámetros propio y deben mapearse explícitamente también.

Validación: todas las coordenadas finitas, x1>x0 e y1>y0, diferencias/scale/dimensiones/matriz comprobadas en cada operación. Una coordenada negativa o cero no es error. Oráculo T14 previo a ejecución: native FS_RECTF{left:-10,top:30,right:90,bottom:-20} produce wire(-10,-20,90,30), ancho100/alto50; scale2/r0 da200x100 y las mismas posiciones relativas de T13. NaN, infinito, igualdad o inversión de extremos rechazan; no normalizar silenciosamente ni confundir wire order con ABI. T14 NOT_RUN; P1 productivo sigue pendiente, actor R2 aceptado sólo como diseño. R1/R2/R3 conservados.

## Delta R5: alfa real y diagnósticos cerrados
