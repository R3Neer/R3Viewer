## Propiedad y vínculo real

Salida HTML exclusivamente PipelineData::Value completo con schema aprobado; Error también permitido. Empty/ListStream/ByteStream en una llamada HTML admitida son UnsupportedGuardedOutput: destruir dato mientras lease retenido y reportar error. No guardar guard en PipelineDataWriter::None ni anunciar streams cubiertos.

Elegir registro/controller de UN slot por companion/SDK connection, financiado explícitamente al crear servicio HTML. Sin HashMap/BTreeMap, Vec de llamadas o tombstones ilimitados. SDK EngineInterfaceState recibe Option<Arc<dyn ValueReplyController>> mediante constructor opt-in; EngineInterface conserva sus fields y Clone existentes, sin nueva Arc por clone ni un slot por interfaz. Constructor legacy None y runner legacy siguen comportamiento actual. Nueva entrada hidden serve_plugin_io_with_value_reply_policy instala controller; wrapper serve_plugin_with_value_reply_policy replica boot nativo del companion opcional. No nuevo PluginCommand ni activation desde encoder/use r3viewer.nu. La feature SDK sólo habilita API; usar API legacy no instala controller, incluso con feature unificada en workspace.

CallKey SDK cerrado = context() PluginCallId + Arc<AtomicBool> de call_signals.interrupt_flag() + identidad del controller de esa connection. El SDK obtiene estos valores de la EngineInterface real, nunca de argumentos/Value/metadata. Clones tienen mismo flag; context con mismo número pero otra invocación tiene Arc distinto. No nonce fabricado, pointernúmero aportado por usuario ni Signals global. Cada alias flag ocupa un handle real incluido en sizeof del key; no duplica cuerpo AtomicBool SDK preexistente. Ausencia de context/flag o controller mismatch => error antes admission. Fuentes actuales acreditan context()/interface_for_context()/Signals::interrupt_flag; no se añade API nu-protocol.

ValueReplyController es trait object Send+Sync+Debug. Implementación privada única HtmlReplyRegistry contiene Mutex<Slot<HtmlCallOwned>>, presupuesto controlado y recibos de allocation fija. HtmlCallOwned es valor concreto inline: ReplyResources (receipts raw/DOM/export/guards), HtmlWorkState y WorkerResidence real, más diagnóstico acotado. Slot guarda Key y payload Option<HtmlCallOwned>; incluso None conserva bytes INLINE completos: se cobra sizeof de TODO Slot/Registry, nunca se resta payload desaparecido. Metadata física fija y Arc header sobreviven hasta último propietario real del servicio/controller; caller Nu después de transferencia queda fuera de ledger. Se preservan docs de opacos SDK/thread/allocator, no cota total shell.

Estados cerrados Idle -> Admitted -> Borrowed -> Admitted -> Sending -> Closing -> Idle. Un fallo admission conserva Idle; Busy desde cualquier estado no Idle. Poisoned deja estado Failed/Pending cerrado y no admite otro parser. No reset por signals.reset ni controller nuevo para esquivar Pending. Status interno distingue Running/Sending/Pending/Closing; no nuevo comando público.

## Métodos y secuencia propuesta

SDK propone ValueReplyController::admit_value_call(&EngineInterface,command_name)->Result<AdmissionDecision,ShellError>, donde AdmissionDecision es Legacy o Admitted(CallKey). Sólo from html/from htm llevan Admitted; cualquier otro comando devuelve Legacy. El controller obtiene key vía accessor hidden EngineInterface::value_reply_key(), cuya construcción es SDK privada. Admission reserva receipts concretos y Work antes copiar Key/crear guard/modificar Slot. Registro duplicado misma Key y otra Key concurrente => AlreadyAdmitted/Busy, no reemplazar payload. El resultado Admitted es prueba sellada del controller; runner valida exacta identidad/key antes usarlo.

En el NUEVO runner opt-in, antes command.run y dentro catch_unwind: policy.admit, instalar ValueReplyRunGuard{controller,key,finished:false}, después command.run. Guard metadata ha sido reservada durante admission antes de construirlo. Si admission falla, no parser ni producto; escribir diagnóstico normal sin lease nuevo. Legacy usa el tramo actual write_response(...).and_then(writer.write).try_to_report sin registro. Guard HTML está vivo durante run, resultado, init, serialize, flush y try_to_report. Por orden lexical result/header/response temporales se destruyen antes del guard exterior; helper retorna sin retenerlos. Los clones del engine pueden acceder al mismo registro, pero NO poseen/copían el payload ni terminan la llamada.

Para el comando/exporter: EngineInterface::with_value_reply_lease<T,R>(closure) usa controller::borrow_lease(key,...). Método genérico sólo admite tipo concreto T registrado y callback con retorno R sin referencias prestadas al payload. Sacar payload inline mediante LoanGuard<T> y marcar Borrowed bajo mutex corto; liberar mutex; ejecutar callback/lectura/parsing/export con &mut T fuera mutex; devolver T al mismo slot bajo mutex corto. Closure puede producir Value completo, receipts quedan en T retornado, y no exporta Arc/clone de receipts; fields/factories HtmlResponseLease son privados. Ningún mutex de registro se mantiene durante source/worker IO, serializer, write, flush o Drop grande. Un segundo préstamo/reply concurrente de un clone devuelve Borrowed/Pending, no toma ni destruye payload. Callback unwind devuelve payload y decrece préstamo en Drop; no habrá publish parcial.

SDK helper privado write_value_response_in(result,&ValueReplyRunGuard) toma sólo transición Sending; usa init_write_pipeline_data actual. Init error llama helper PRIVADO de error con EL MISMO guard, nunca write_response público que vuelva a claim. Helper de error de try_to_report conserva mismo préstamo del guard y semántica ReportedError/UnreportedError existente: el guard abarca el segundo intento de error. Ningún init_error/reintento retira entrada o permite segunda admission. Double successful reply por otro clone/otro runner de misma Key se rechaza; sólo helper de error interno puede continuar una tentativa ya iniciada. No se añade propagación al writer stream.

Success sólo tras write y flush OK, marcado terminal por guard; error no se etiqueta respuesta entregada. Error de init/serialize/write/flush/reporte deja Failed terminal cuando ownership físico haya terminado; callback de usuario run Err aún conserva receipts hasta reportar error. Writer arbitrario bloqueado => guard y cargo vivo, status Pending/Busy, siguiente llamada no parser. No deadline que finja liberar Value en writer ni mutex que bloquee status/cancel. Busy error puede a su vez esperar al writer global SDK: eso no bloquea consulta interna al registry, y no prometemos cap de threads/requests Nu preexistentes.

Al terminar/unwind: RunGuard informa ReplyPhysicalEnd sólo después de destruir los temporales Value/header/response y terminar sus préstamos. Closing NO confirma Idle por ese hecho: requiere también WorkerClosed/NeverSpawned sellado del MISMO HtmlCallOwned. Si worker está Running/Reaping/Pending, conservar bundle, Child/Job/pipes/threads/source/cargos en el mismo slot o su único ReapGuard; errorwrite+flushOK no retira payload ni abre gate. Sólo conjunción de ambas pruebas y Drop físico final del bundle fuera mutex permite Idle. No reset de Work, nuevo owner o segundo allowance. Reentrancia Borrowed conserva Closing/Pending y reap del mismo owner. SDK/controller/owner shutdown también conserva Pending físicamente; último Drop no sustituye cleanup. El apartado R2 concreta pruebas/admisión/reap; tiene precedencia sobre R1.

Panic durante run/helper/serializer hace unwind de los objetos y guard; comportamiento externo SDK actual process::exit(1) se conserva después catch. No afirmar Rust Drop donde hay abort/proceso exit, ni respuesta válida; recuperación de worker parser ya pertenece a HTML-STATIC-DOM y no debe escapar como panic del command. Calls rechazadas antes policy, Signature/Metadata/completions y errores de input de manager siguen Legacy sin lease inexistente.
